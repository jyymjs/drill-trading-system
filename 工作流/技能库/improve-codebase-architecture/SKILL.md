# 架构审计与改进

从架构层面审查代码，不只关注单行逻辑，更关注模块间关系和演进方向。

## 审查维度

### 1. 依赖方向

- 上层依赖下层？还是反过来？
- 是否存在循环依赖？
- 是否违反依赖倒置原则（高层模块依赖低层实现细节）？

### 2. 模块边界

- 模块职责单一？还是混合多种关注点？
- 模块间接口清晰？还是通过隐式共享状态通信？
- 公共接口 vs 内部实现是否分明？

### 3. 命名与术语

- 命名是否符合项目统一术语（对照 `CONTEXT.md` 若存在；术语定义见 domain-modeling 技能）？
- 同一概念在不同模块中是否使用一致名称？
- 是否有"神秘命名"（Mysterious Name，名称不能揭示其用途）？

### 4. 分层合规

根据项目架构规范（部门 CLAUDE.md / 架构文档）定义的层级结构检查：

- 各层之间是否通过定义好的接口通信？
- 是否有跨层调用？
- 新增代码是否放在正确的层？

### 5. 演进方向

- 新增代码是否让架构往更清晰的方向发展？
- 还是增加了技术债务？
- 是否存在"散弹式修改"（Shotgun Surgery，一个逻辑变更需修改多个文件）？

## 审查报告格式

```
## 架构合规
- ✅ 依赖方向：新增模块遵循自上而下依赖
- ❌ 模块边界：scanner.py 混合了数据获取和展示逻辑，建议拆分
- ⚠️ 命名：get_data() 在不同模块中含义不同（获取行情 vs 获取配置）
```

## 改进建议

发现架构问题时，提供具体改进方案而非笼统批评：
- ❌ "模块耦合太高"
- ✅ "scanner.py 第 45-78 行的数据解析逻辑应提取到 data/parser.py，让 scanner 只负责调度"
