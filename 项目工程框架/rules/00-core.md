# 核心原则

## R1: Human steers, Agent executes
- 人类定义目标，Agent 负责执行路径
- 任何影响项目核心结果的操作须经人类确认
- Agent 可提出建议但不得擅自执行关键变更

## R2: 可追溯性
- 每次变更须关联到任务描述
- 重要决策写入规划确认书

## R3: 渐进交付
- 子任务粒度：一个可独立测试的功能点
- 每个子任务通过独立审查后各自合并

## R4: 规则来自失败
- 每条规则对应一次真实 Agent 失败
- 不写预防性规则
- 同类错误不允许犯第二次

## R5: 需求确认闸门（2026-08-01 失败沉淀）
- 用户提出**新需求或需求变更**时，规划部只做两件事：① 拷问澄清 ② 更新规划确认书
- **任何实现动作（创建/修改/删除文件、建目录、移动文件、运行实现脚本）在用户明确签字前一律禁止**
- 「签字」= 用户对确认书的明确同意；**沉默、提出新需求、间接信号（如"继续做"）都不算签字**
- 例外：技术可行性验证（只读探测、临时脚本、不落盘正式文件）属规划部职责，不受此限；验证产物须标注临时性，与正式实现分离
- 流程说明（2026-08-02）：签字前可经助理预审上呈（助理只过滤与转呈，**不替代用户签字**）；技术性修订（规划部内部调整、不改变业务目标）可由助理按决策分级自主批准
- **执行确认机制（2026-08-02 教训沉淀）**：任何修改类方案执行前必须**主动询问**，收到用户明确"确定"才动手；"大概/考虑/规划/修改一下"一律视为讨论信号，只出方案不动手；拿不准先问"这是讨论还是执行？"
- 失败案例：2026-08-01 用户在未确认的需求下连提三项变更（模式A/独立目录/产出分类），规划部直接动手实现，违反 R1 与 R5

## R6: 规范变更必须连带旧实现对齐（2026-08-01 失败沉淀）
- 任何「规范升级」类变更，拆解子任务时必须包含**所有现有实现的对齐项**（脚本输出命名、模板、文档引用等），不能只改新代码留旧实现脱节
- 判断方法：规范变更后，逐个问「哪些已存在的代码/文件按旧规范产出？」——全部列入子任务
- 失败案例：raw 命名规范升级到 v1.4 后，fetch.py 输出仍按旧格式 `{BV号}.md`（子任务 3 范围漏了对齐项），审查环境验证才暴露（B1 阻塞）

## R7: 工程部主动提醒必须登记闭环（2026-08-01 失败沉淀）
- 工程部汇报中主动提出的遗留问题/待办（如"建议后续对齐"），规划部**必须登记进 todo 跟踪并安排处理**，不得看过即过
- 处理方式：安排给相关子任务（后续任务补入）或立即派发；登记后如本次不处理，需在交付说明中注明遗留
- 失败案例：工程部 Y 汇报 fetch.py 输出命名未对齐时主动提醒，规划部未登记未闭环，拖至审查暴露（B1）
